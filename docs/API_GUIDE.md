# API — быстрый старт и сценарии

Swagger UI: `http://localhost:8000/api/docs/swagger/`  
OpenAPI JSON: `http://localhost:8000/api/schema/`  
ReDoc: `http://localhost:8000/api/docs/redoc/`

## Как выполнять запросы в Swagger

1. Войдите через `POST /api/v1/auth/token/` — укажите email и пароль существующего пользователя.
2. Скопируйте `access` из ответа, нажмите **Authorize** и вставьте только токен (без `Bearer`).
3. Откройте endpoint → **Try it out** → заполните поля → **Execute**.
4. Успешные ответы имеют обёртку `success`, `data`, `error`. В `data` находится результат операции.

`refresh` хранится в HttpOnly-cookie браузера. Обновление токена выполняйте в том же браузере через `POST /api/v1/auth/token/refresh/`.

# B2B Supply Platform — User Scenarios

Документация основных пользовательских сценариев платформы B2B Supply Platform: публикация каталога поставщика, импорт прайс-листов, оформление и оплата заказов, генерация документов, управление сотрудниками и восстановление пароля.

## Сценарий 1. Поставщик публикует каталог

Нужен пользователь с ролью `SUPPLIER_ADMIN` в подтверждённой организации.

1. Создайте склад: `POST /api/v1/warehouses/`.

```json
{
  "name": "Основной склад",
  "address": "Москва, ул. Пример, 1"
}
```

2. Загрузите прайс-лист (сценарий 2). В колонке `warehouse` укажите точное имя созданного склада — `Основной склад`.
3. Проверьте результат импорта через `GET /api/v1/price-list/{import_id}/`.
4. После завершения импорта найдите опубликованный товар:

`GET /api/v1/products/?search=название`

Товары создаются или обновляются на основании данных прайс-листа. Информация о доступных остатках привязывается к соответствующему складу.

## Сценарий 2. Импорт прайс-листа Excel

Нужен пользователь `SUPPLIER_ADMIN` подтверждённой организации и активный склад.

Поддерживаемые форматы: `.xlsx`, `.xls`.

1. Получите ссылку для загрузки файла:

`POST /api/v1/price-list/upload-url/`

```json
{
  "file_name": "price-list.xlsx"
}
```

2. Выполните `PUT` на полученный `upload_url`, передав бинарное содержимое Excel-файла.

```bash
curl -X PUT "<upload_url>" \
  --upload-file price-list.xlsx \
  -H "Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"
```

3. Запустите импорт:

`POST /api/v1/price-list/`

```json
{
  "storage_key": "<storage_key из ответа>",
  "original_name": "price-list.xlsx"
}
```

4. Сохраните `id` из ответа и проверяйте состояние импорта:

`GET /api/v1/price-list/{id}/`

Опрос выполняется до получения конечного статуса.

Excel-файл должен содержать следующие заголовки:

| Колонка | Назначение |
|---|---|
| `sku` | Артикул товара |
| `name` | Название товара |
| `price` | Цена |
| `warehouse` | Название склада |
| `quantity` | Количество товара |

`warehouse` — точное имя существующего активного склада поставщика.

Импорт создаёт или обновляет товары и соответствующие складские остатки.

Возможные статусы импорта:

- `PENDING` — ожидает обработки.
- `PROCESSING` — выполняется обработка.
- `COMPLETED` — импорт завершён.
- `COMPLETED_WITH_ERRORS` — импорт завершён с ошибками.
- `FAILED` — импорт завершился неудачно.

## Сценарий 3. Покупатель оформляет заказ и оплачивает его

Необходимы подтверждённые организации покупателя и поставщика, опубликованный товар и доступный складской остаток.

Для создания заказа пользователь должен иметь роль покупателя.

1. Найдите товар:

`GET /api/v1/products/?search=название`

2. Из ответа получите:
   - UUID товара (`id`);
   - UUID склада (`warehouses[].id`);
   - UUID организации поставщика (`supplier.id`).

3. Создайте заказ:

`POST /api/v1/orders/`

```json
{
  "supplier": "<supplier_uuid>",
  "items": [
    {
      "product": "<product_uuid>",
      "warehouse": "<warehouse_uuid>",
      "quantity": 2
    }
  ]
}
```

4. Сохраните `id` созданного заказа.

После создания заказ получает статус `RESERVED`. Количество товара резервируется на соответствующем складе.

5. Создайте платёж:

`POST /api/v1/payments/`

```json
{
  "order_id": "<order_uuid>"
}
```

6. Получите `confirmation_url` из ответа и откройте ссылку для завершения оплаты через YooKassa.

После успешного подтверждения платежа через webhook заказ получает статус `PAID`.

7. Поставщик подтверждает оплаченный заказ:

`POST /api/v1/orders/{order_id}/confirm/`

Для выполнения операции пользователь должен иметь роль поставщика и доступ к соответствующему заказу.

Пример запроса:

```bash
curl -X POST \
  "http://localhost:8000/api/v1/orders/<order_uuid>/confirm/" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json"
```

После успешного выполнения операции основной сервис переводит заказ в статус `CONFIRMED`.

### 8. Автоматическая генерация документов (Documents Service)

После подтверждения заказа запускается асинхронный процесс генерации документов.

Взаимодействие основного сервиса и микросервиса документов происходит через RabbitMQ.

**Этап 1. Формирование события в основном сервисе**

При подтверждении заказа `b2b-supply-core` создаёт событие:

```text
order.confirmed
```

Для события используются:

- Exchange: `b2b.events`
- Exchange type: `topic`
- Routing key: `order.confirmed`

Событие содержит информацию о заказе, покупателе, поставщике, товарах, складах, количестве, стоимости и итоговой сумме.

Для публикации используется механизм Outbox.

**Этап 2. Получение события микросервисом документов**

`documents-service` подписан на RabbitMQ и слушает очередь:

```text
documents.events
```

Очередь привязана к exchange `b2b.events` по routing key:

```text
order.confirmed
```

При получении события микросервис:

1. Декодирует JSON-сообщение.
2. Валидирует данные заказа через `InvoiceGeneratePayload`.
3. Передаёт задачу генерации счёта в Celery.

**Этап 3. Генерация PDF-счёта**

Celery Worker выполняет задачу:

```text
documents.generate_invoice
```

В процессе выполнения:

1. Проверяется наличие ранее созданного счёта для заказа.
2. Загружается HTML-шаблон `orders/invoice_template.html`.
3. Данные заказа передаются в Jinja2.
4. WeasyPrint преобразует HTML в PDF.
5. PDF-файл загружается в S3/MinIO.
6. Информация о документе сохраняется в базе данных `documents-service`.

Для счёта используются:

```text
DocumentType: invoice
Content-Type: application/pdf
Storage key: invoices/invoice_<order_uuid>.pdf
```

Название файла формируется по шаблону:

```text
Счет-заказ №<order_number>.pdf
```

Генерация выполняется асинхронно, поэтому подтверждение заказа и готовность документа не происходят одновременно.

**Этап 4. Получение документов заказа**

Для получения документов используется API микросервиса `documents-service`.

Endpoint:

```http
GET /api/v1/documents/{order_id}/
```

Где `order_id` — UUID заказа.

Пример запроса:

```bash
curl -X GET \
  "http://localhost:8002/api/v1/documents/<order_uuid>/" \
  -H "Authorization: Bearer <access_token>"
```

Необходимо передавать действующий JWT Access Token в заголовке `Authorization`.

Перед выдачей документов микросервис проверяет доступ пользователя к заказу через основной сервис:

```http
GET /api/v1/orders/{order_id}/exists/
```

Проверка выполняется с передачей пользовательского токена.

Если заказ не существует или организация пользователя не имеет к нему доступа, микросервис возвращает `404 Not Found`.

В настоящий момент для подтверждённого заказа автоматически генерируется PDF-счёт (`invoice`).

Ссылка `download_url` является предварительно подписанной S3-ссылкой. Время её действия — 300 секунд (5 минут).

**Важно:** если генерация ещё не завершилась, API вернёт пустой массив:

```json
[]
```

Это не означает ошибку подтверждения заказа. Необходимо повторить запрос через некоторое время.

### 9. Отмена заказа

Покупатель может отменить заказ, если его текущий статус допускает отмену.

Endpoint:

`POST /api/v1/orders/{order_id}/cancel/`

При отмене:

- Заказ получает статус `CANCELLED`.
- Связанные активные резервы освобождаются.
- Если заказ уже оплачен, выполняется вызов отмены платежа через YooKassa.

## Сценарий 4. Приглашение сотрудника

Нужен администратор организации (`SUPPLIER_ADMIN` или `BUYER_ADMIN`).

1. Создайте приглашение:

`POST /api/v1/organizations/my-company/invites/`

```json
{
  "email": "employee@example.com",
  "role": "BUYER_MANAGER"
}
```

Допустимые роли:

- `SUPPLIER_ADMIN`
- `SUPPLIER_MANAGER`
- `WAREHOUSE_MANAGER`
- `BUYER_ADMIN`
- `BUYER_MANAGER`

Роль должна соответствовать типу организации.

2. Получатель открывает ссылку из письма. Frontend передаёт токен:

`POST /api/v1/organizations/my-company/invites/accept/`

```json
{
  "token": "<invite_token>"
}
```

3. Если `is_new_user: true`, необходимо завершить регистрацию через:

`POST /api/v1/organizations/my-company/invites/register/`

Передаются следующие данные из ответа предыдущего шага:

- `registration_token`
- `first_name`
- `last_name`
- `username`
- `password`

После завершения регистрации пользователь получает доступ к организации в соответствии с назначенной ролью.

## Сценарий 5. Восстановление пароля

1. Запросите OTP-код:

`POST /api/v1/auth/request-otp/`

```json
{
  "email": "user@example.com"
}
```

2. Получите код из электронной почты и подтвердите его:

`POST /api/v1/auth/verify-otp/`

```json
{
  "email": "user@example.com",
  "otp": "123456"
}
```

3. Используйте `reset_token` из ответа для сброса пароля:

`POST /api/v1/auth/reset-password/`

Передайте `reset_token`, `new_password` и `confirm_password`.

## Полезные API-запросы

### Авторизация и организации

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/api/v1/auth/me/` | Информация о текущем пользователе и его роли |
| GET | `/api/v1/organizations/my-company/` | Информация об организации и её статусе верификации |

### Каталог и складские остатки

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/api/v1/products/` | Получение каталога товаров |
| GET | `/api/v1/stocks/` | Получение складских остатков |
| GET | `/api/v1/stocks/reports/` | Отчёты по остаткам, резервам и доступному количеству |
